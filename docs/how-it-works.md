# Как расширение следит за изменениями задач

Простое описание алгоритма — без погружения в код. Документ на русском, потому что
написан для автора форка; в коде всё то же самое отражено в `background.js`,
`List.vue` и `utils/changes.js`.

## Общая идея: два этажа

Расширение никогда не качает всё сразу. Работа разделена на два этажа:

```
Этаж 1 (фон, сам по себе):   список задач → сравнение → "что обновилось"
Этаж 2 (фон + попап):        журнал задачи → счётчик, панель изменений, тултип
```

Фон работает всегда и дёшево. Тяжёлые данные (комментарии, история изменений)
качаются один раз на изменение задачи — фоном сразу после цикла опроса — и
дальше живут в кэше, из которого их берёт попап.

## Этаж 1. Фоновый опрос (каждые N минут)

Каждые `interval` минут (настройка «Интервал обновления») фон делает лёгкий
запрос: `GET /issues.json` — список задач. Это «карточки» задач: id, тема,
статус, приоритет, трекер, проект, `updated_on`. Истории и комментариев в них
нет, ответ маленький.

В запросе:

- **роли** — три отдельные выборки: «Назначенные мне», «Мои», «Наблюдаемые»;
- **фильтры** — статусы, проекты, трекеры из настроек;
- **топ-N** — не все задачи, а N последних по изменению (настройка
  «Количество задач»; N больше 100 качается страницами).

Redmine **не умеет** отдавать «только изменённые с момента X». Поэтому качается
срез «последние N изменённых», а сравнение с прошлым срезом делается у нас
локально.

### Что такое `updated_on`

Это поле самой задачи в Redmine: отметка времени последнего изменения.
Добавили комментарий, сменили статус или исполнителя, прикрепили файл —
сервер сдвинул `updated_on`. Плагин это поле только читает.

Нюанс: `updated_on` может дёрнуться «без причин» — например, при изменении
подзадачи у родителя. Тогда задача честно считается обновлённой, но новых
записей в журнале нет. Фон это проверяет (см. «Фантом-автопрочтение» ниже),
поэтому заглушка «Задача обновлена» в попапе почти не встречается.

### Сравнение и непрочитанные

Каждая версия задачи получает технический идентификатор:
`uuid = id задачи + updated_on`. Если uuid задачи в новом ответе отличается
от сохранённого — задача обновилась. Такие задачи попадают в список
непрочитанных:

- на иконке расширения появляется бейдж с числом непрочитанных **задач**;
- срабатывают десктоп-уведомления (если статус входит в «Статус уведомлений»).

На этом этаже журналы НЕ качаются. Только список и сравнение.

## Этаж 2. Журналы задач

Кто качает журнал задачи:

1. **Фон** — сразу после цикла опроса, для задач, ставших непрочитанными
   в этом цикле (см. «Фоновый префетч журналов» ниже). Пока пользователь
   откроет попап, всё уже лежит в кэше.
2. **Попап** — по запросу: раскрытие строки, тултип, окно задачи; если
   кэша нет (или версия устарела), делается один полный запрос.
   Как fallback попап сам префетчит до 30 непрочитанных при открытии.

Запрос один и тот же: `GET /issues/:id.json?include=journals` — весь журнал
задачи. Ответ тяжёлый: на боевых задачах бывает по 100–200 записей. Из
журнала берутся записи новее «точки отсчёта» — это и есть непрочитанные
изменения задачи. Тот же источник данных используется для hover-тултипа по
строке («последнее изменение») и для окна задачи.

### Точка отсчёта («что считать непрочитанным»)

Каждая роль хранит две метки времени:

- `lastRead` — когда нажали «Пометить все как прочитанные»;
- `readAt[id]` — когда конкретную задачу пометили прочитанной (клик по строке).

Точка отсчёта задачи = более поздняя из них. Всё, что в журнале новее этой
точки, считается непрочитанным. Клик по строке сдвигает точку на «сейчас» —
счётчик задачи обнуляется.

**При первом подключении** точки отсчёта ещё нет. Фон берёт её из самого
первого успешно скачанного среза: `lastRead = самая свежая updated_on` в
срезе (серверное время — расхождение часов не страшно). В итоге чистая
установка показывает **ноль непрочитанных**, попап не качает ни одного
журнала и не показывает тостов «из прошлого»; дальше считаются только новые
изменения. Если запрос роли упал, роль получит бейзлайн при следующем цикле.

### Фоновый префетч журналов

Сразу после каждого цикла опроса фон скачивает полные журналы задач,
ставших непрочитанными **в этом цикле** (обычно 0–5 штук, не больше 10,
по 4 запроса параллельно) — ещё до того, как пользователь откроет попап.
Благодаря этому счётчики и тултипы в попапе уже тёплые: всё берётся из кэша.

### Фантом-автопрочтение

Скачав журнал свеженепрочитанной задачи, фон проверяет: есть ли в журнале
хоть одна запись новее точки отсчёта? Если нет (updated_on дёрнулся
подзадачей и т.п.) — задача помечается прочитанной молча: без уведомлений,
без заглушки «Задача обновлена», без клика. Время прочтения — серверное
`updated_on` самой задачи.

### Счётчик на строке задачи

Число на синем кружке = **все** непрочитанные записи задачи: комментарии,
смены статуса/исполнителя/приоритета, вложения — каждая запись журнала даёт +1.
Число не ограничено настройками и растёт, пока задача не прочитана.

### Лимит «Максимум изменений в списке»

Настройка влияет **только на отображение**, не на скачивание:

- в раскрытой панели показываются последние N записей (хронологически, как
  тред: сверху старейшая из показанных, снизу новейшая);
- счётчик при этом показывает точное полное число;
- под списком — подпись «Показаны последние N из M»;
- при появлении новой записи окно сдвигается: верхняя строка выпадает из
  отображения (но остаётся в счётчике, в кэше и, разумеется, в самом Redmine).

Скачивание лимит урезать не может: API Redmine отдаёт журнал задачи только
целиком, «последние N записей» запросить невозможно.

## Кэши

Качать по 200 записей при каждом открытии попапа — слишком дорого. Поэтому
есть два постоянных кэша в локальном хранилище расширения — **раздельные,
под разные потребности**:

**Кэш журналов (`journal_cache`, до 40 задач)** — полные журналы для
счётчиков и панели изменений:

- каждый скачанный журнал сохраняется (ключ — id задачи, актуальность — по
  `updated_on`);
- пока `updated_on` задачи не изменилась, попап берёт её журнал из кэша —
  мгновенно и без сети;
- изменилась — один полный запрос, и снова в кэш;
- кэш ограничен (40 задач, длинные тексты обрезаются с запасом), самые
  старые вытесняются.

**Кэш тултипов (`tooltip_cache`, до 300 задач)** — заглушки «последнее
изменение» для мгновенного hover-тултипа по строке:

- хранится уже **отрендеренная** последняя запись (автор, время, строки
  изменений) — показывается без запросов и без карт имён;
- пишется при каждом полном рендере журнала в попапе, а также при
  вытеснении задачи из кэша журналов (там raw-запись, попап дорисовывает);
- задачи из этого кэша не обязаны быть в кэше журналов — поэтому тултип
  мгновенный даже для давно виденных задач.

Оба кэша сбрасываются при смене сервера в настройках (вместе с состоянием
прочтения) — иначе ids задач разных серверов перемешались бы.

Итоговый трафик: лёгкие списки каждые N минут + тяжёлый журнал один раз на
задачу по факту её изменения (фон делает это сам, без открытия попапа);
всё остальное — из кэшей.

## Смена сервера

При сохранении настроек расширение сравнивает адрес и API-ключ с прежними.
Если что-то изменилось — очищаются `data`, `journal_cache` и
`tooltip_cache` (папки не трогаются — это пользовательские данные).
Следующий цикл опроса даёт новому серверу собственный бейзлайн «первого
подключения».

## Шпаргалка «кто за что отвечает»

| Что | Где живёт | Когда обновляется |
|---|---|---|
| Список задач и непрочитанность | `data` в хранилище | фоновый опрос, каждые N минут |
| Бейдж на иконке (число непрочитанных задач) | Chrome API | там же |
| Десктоп-уведомления | — | там же |
| Бейзлайн при первом подключении | `lastRead` в `data` | первый успешный опрос роли |
| Журналы задач (изменения, комментарии) | кэш `journal_cache` | фоновый префетч после цикла / попап, только изменившиеся |
| Тултип «последнее изменение» | кэш `tooltip_cache` | каждый полный рендер журнала + вытеснение из journal_cache |
| Фантом-автопрочтение | `data` | фон, после скачивания журнала |
| Точка отсчёта прочитанности | `lastRead` / `readAt` в `data` | клик по строке / «пометить все» |
| Счётчик на строке (непрочитанные записи) | память попапа | из журнала + кэша |
